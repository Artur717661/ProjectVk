# Развёртывание с нуля — пошагово

Инструкция для чистого ноутбука на Windows 10/11. Всё, что нужно установить, —
это Docker Desktop; Python, Postgres, Kafka и остальное ставить **не надо**, они
поднимутся в контейнерах.

Нужно: права администратора, ~6 ГБ свободного места, интернет (для первой сборки).

---

## Шаг 1. Установить Docker Desktop

1. Скачать: **https://www.docker.com/products/docker-desktop/** → «Download for Windows».
2. Запустить `Docker Desktop Installer.exe`. Галочку **«Use WSL 2 instead of Hyper-V»** оставить включённой.
3. Дождаться установки и **перезагрузить компьютер** (установщик попросит).
4. После перезагрузки **запустить Docker Desktop** из меню Пуск (иконка кита).
   Подождать, пока иконка в трее перестанет анимироваться и появится статус
   «Engine running» — при первом старте это 1–2 минуты.

Проверка (в PowerShell):

```bash
docker --version
```

```bash
docker compose version
```

Обе команды должны вывести версии. Если пишет «command not found» — Docker Desktop
не установлен или не запущен.

---

## Шаг 2. Забрать код

Нужен Git: если его нет — **https://git-scm.com/download/win** (установка «Далее-Далее»).

```bash
git clone -b feature/photo-service https://github.com/Artur717661/ProjectVk.git
```

```bash
cd ProjectVk
```

Файл `.env` уже лежит в репозитории со значениями по умолчанию — создавать
и настраивать ничего не нужно.

---

## Шаг 3. Поднять всё одной командой

```bash
docker compose up -d --build
```

**Первый запуск идёт 5–10 минут** — скачиваются образы (Postgres, Kafka, MinIO,
Prometheus, Grafana) и собираются два наших образа. Последующие запуски —
секунды.

Что происходит под капотом: поднимаются Postgres/MinIO/Kafka, дожидаются
healthcheck'ов, затем разово отрабатывает сервис `migrate` (`alembic upgrade
head`), и только после него стартуют `api` и `worker`.

Проверить, что всё поднялось:

```bash
docker compose ps
```

Все сервисы должны быть в статусе `running` (у `migrate` будет `exited (0)` —
это нормально, он одноразовый).

---

## Шаг 4. Проверить, что сервис живой

```bash
curl http://localhost:51201/healthz
```

```bash
curl http://localhost:51201/readyz
```

`/readyz` должен вернуть `{"status":"ready", ...}` — он реально проверяет
соединение с базой, MinIO и Kafka.

Что открыть в браузере:

| Что | Адрес | Логин |
|---|---|---|
| **Swagger (API)** | http://localhost:51201/docs | — |
| Метрики Prometheus-формата | http://localhost:51201/metrics | — |
| MinIO Console | http://localhost:51203 | `minioadmin` / `minioadmin` |
| Prometheus | http://localhost:51204 | — |
| Grafana | http://localhost:51202 | `admin` / `admin` |

## Шаг 5. Прогнать полный путь фотографии

Загрузить любое изображение (подставьте свой путь к файлу):

```bash
curl -F "file=@C:/Users/Public/Pictures/photo.jpg" http://localhost:51201/v1/photos
```

Ответ должен быть `202` вида:

```json
{"photo_id":"3f1c...","status":"pending"}
```

Через пару секунд запросить статус (подставьте свой `photo_id`):

```bash
curl http://localhost:51201/v1/photos/ВАШ_PHOTO_ID
```

Ожидаемо статус станет `done`, и появятся результаты анализа: `faces_count`,
`is_blurred`, `blur_score`, `perceptual_hash`, `tags`, `model_version`.

Проверить, что файл реально лёг в хранилище: откройте MinIO Console
(http://localhost:51203), бакет `photos` → папка с вашим `photo_id`.

Удобнее всё то же самое делать через Swagger: http://localhost:51201/docs →
`POST /v1/photos` → «Try it out» → выбрать файл → Execute.

## Шаг 6. Если внешний анализатор недоступен

Анализ выполняет внешний сервис `45.132.19.101:50051`. Если он не отвечает (нет
сети, сервер лёг), фото будет уходить в статус `failed` с
`last_error_code: analyzer_unavailable`.

На этот случай в проекте есть **локальный mock-анализатор** — поднимается тем же
compose, полный путь загрузки при этом работает целиком:

```bash
docker compose -f docker-compose.yml -f docker-compose.mock.yml up -d --build
```

Он реализует тот же самый `.proto`-контракт и возвращает детерминированные
результаты — для демонстрации работоспособности этого достаточно.

## Полезные команды

Посмотреть логи (JSON-логи с `photo_id` и `request_id`):

```bash
docker compose logs -f api
```

```bash
docker compose logs -f worker
```

Прогнать тесты:

```bash
docker compose run --rm api pytest -v
```

Остановить всё (данные сохранятся):

```bash
docker compose down
```

Остановить и стереть данные (чистый старт с нуля):

```bash
docker compose down -v
```

Пересобрать после изменений в коде:

```bash
docker compose up -d --build
```

## Если что-то пошло не так

**`docker: command not found` / `Cannot connect to the Docker daemon`**
Docker Desktop не запущен. Откройте приложение из Пуска и дождитесь «Engine running».

**`port is already allocated`**
Порт занят другой программой. Все внешние порты заданы в `docker-compose.yml`
(51201–51204) — поменяйте левое число в паре `"51201:8000"` на свободное.

**`api` или `worker` в статусе `restarting`**
Посмотрите причину: `docker compose logs api`. Чаще всего это значит, что
миграции не отработали — проверьте `docker compose logs migrate`.

**Фото зависает в `pending`**
Не работает воркер или Kafka. Смотрите `docker compose logs worker`.

**Фото уходит в `failed`**
Смотрите поле `last_error_code` в ответе `GET /v1/photos/{id}`. Если там
`analyzer_unavailable` — внешний анализатор недоступен, поднимайте с
mock-анализатором (Шаг 6).

**Первая сборка висит очень долго**
Это нормально для первого раза (скачивание образов + установка Python-зависимостей).
Прогресс видно в выводе команды.
