# Архитектура проекта

## Что решает сервис

В медиатеке трудно вручную искать неудачные и похожие фотографии. Сервис
принимает фотографию, сохраняет её и возвращает клиенту состояние обработки.
Позже worker передаст её отдельному analyzer, который определит размытие,
лица, закрытые глаза и похожие кадры.

В первых двух воркшопах реализован только первый вертикальный срез:

```text
Client -> FastAPI -> PostgreSQL
                  -> MinIO
```

## Полная схема, к которой мы идём

```text
Client
  |
  | HTTP / REST / multipart
  v
API service -----> PostgreSQL
  |                    |
  |                    +-- статусы и результаты
  v
MinIO (байты фото)
  |
  +-- позже: Kafka -> Worker -> gRPC -> Python analyzer
```

API отвечает за HTTP-контракт, проверку файла, запись метаданных и сохранение
объекта в MinIO. PostgreSQL является источником правды о состоянии фотографии.
Сам файл в базу не кладётся.

## Сценарий upload

1. Клиент отправляет `POST /v1/photos`.
2. API проверяет тип и размер файла.
3. API создаёт `photo_id` и сохраняет файл в MinIO.
4. API записывает фотографию в PostgreSQL со статусом `pending`.
5. Клиент получает `202 Accepted` и идентификатор.
6. Сейчас на этом сценарий заканчивается. После третьего воркшопа API будет
   публиковать задачу в Kafka, а worker — обновлять статус и результат.

## Ответственность компонентов

| Компонент | Ответственность сейчас | Следующий этап |
| --- | --- | --- |
| API service | HTTP, валидация, сервисный сценарий | Создание analysis job |
| PostgreSQL | Метаданные, статус и будущий результат | Источник правды для worker |
| MinIO | Байты фотографий | Чтение файла analyzer-ом |
| Kafka | Не подключена | Надёжная доставка задач |
| Worker | Не подключён | Вызов analyzer, retry, статусы |
| Python analyzer | Контракт подготовлен | Компьютерное зрение |

## Статусы фотографии

`pending` — файл принят и ожидает обработки.

`processing` — worker взял задачу в работу.

`done` — результат анализа сохранён.

`failed` — обработка закончилась ошибкой; причина хранится в полях ошибки.

## Данные

Таблица `photos` хранит имя, MIME-тип, размер, `object_key`, статус, число
попыток, поля будущего анализа и временные метки. В дальнейшем можно вынести
результаты в отдельную `analysis_results`, а похожие кадры — в
`duplicate_groups`, как обсуждалось на первом воркшопе.

## Внутренний контракт analyzer

Внешний клиент общается с API через HTTP/JSON. Worker в будущем будет общаться
с analyzer через типизированный gRPC-контракт из `proto/photo_analyzer.proto`.
В Kafka передаём только `job_id`, `photo_id`, `object_key` и номер попытки — не
сам файл.

## Наблюдаемость и ошибки

Важные события пишутся в JSON-логах. В них есть `request_id`, а для операций с
файлом ещё и `photo_id`. Это позволяет найти всю историю конкретной фотографии.

Сейчас `/metrics` отдаёт базовый счётчик загруженных фотографий. Полноценные
Prometheus, Grafana и алерты появятся позже, когда добавятся worker и Kafka.

Пользовательские ошибки отличаются от проблем зависимостей:

- `415` — неподдерживаемый тип;
- `413` — слишком большой файл;
- `404` — фотография не найдена;
- `503` — временно недоступны PostgreSQL или MinIO;
- `500` — непредвиденная ошибка приложения.
